# ChapterFlow 两版本落地计划：先交付能连载的 AI 开书

制定日期：2026-09-09。产品：ChapterFlow / 文织·网文工坊。

本文件依据用户最新要求收敛发布范围。V1 的验收以本文为准；原 Phase 0/1/2/4、M0—M9 文档保留为长期设计和缺口资料，不能继续作为 V1 必须全部完成的清单。本文是计划和源码审计结论，不是发布验收报告。

## 1. 为什么已经跑了两天，仍感觉不能用

现有底座并非空白：原生作品库、AI 开书候选、大纲、设定、写作台、连续创作、任务恢复、检查修订、导出都有实现。但此前目标同时要求完整旧平台迁移、四视口、双存储模式、导入恢复、复杂共创、指标管理等。按模块不断补齐，容易积累很多局部完成，却没有优先证明“作者输入一个构思后拿到五章可连载正文”。这是目标与验收方式的偏差，不能仅据此归因于 Luna 的能力。

具体证据：

- `07-luna-goal-prompt.md` 原目标要求 M0—M9 全量完成，并把大量原生迁移放在网文主链前面。
- `scripts/autopilot-real-smoke.ts` 已有真实模型集成场景，但开书偏好 `wordsPerChapter: 350`，章节策略 `minChapterCharacters: 180`；使用 Fastify inject，并设置 `enableRunWorker: false`，由脚本调用 advance 推进。它对引擎有价值，不能替代正常浏览器、后台 worker 和足量正文验收。
- `packages/llm/src/adapters/openai-chat.ts` 已支持兼容调用、流式正文、reasoning_content、工具和结构化输出；这不是 DeepSeek V4 Flash 全流程实测通过的证据。结构化默认 json_schema 与 json-mode 分支、推理参数和输出预算仍需按供应商验证。
- 既有审计记录 807 个单元/集成测试通过，浏览器 45 passed / 19 skipped。这些是历史检查结果，本次未重跑；没有找到足以宣称真实 DeepSeek 五章连载完成的发布证据。测试数量不能衡量文学质量。
- `autopilot-coordinator.ts`、`story-context.ts` 已有任务协调和权威设定上下文；不能把一致性机制说成全无，也不能把机制存在等同于连续五章事实、时间和人物行为正确。

不再给未经定义的整体完成百分比。以后只汇报本版本验收门通过了几项、剩余阻塞是什么。

## 2. 两版边界

| 项目     | V1：AI 开书与连载首发                                   | V2：AI 与作者持续共创                               |
| -------- | ------------------------------------------------------- | --------------------------------------------------- |
| 核心价值 | 构思到大纲、设定、五章正文、质检、导出一次跑通          | 作者随时介入、改方向、比较与合并，长篇持续演进      |
| 创作方式 | AI 主导，开书方案和最终稿由作者确认，可明确授权限定批次 | 精细选区、对话改稿、多候选、分支、章节/设定协同修改 |
| 模型     | 官方 DeepSeek V4 Flash，一个明确可用组合                | 多模型分工、路由、偏好和成本优化                    |
| 规划     | 全书主线与终局、分卷、首卷展开、前 10 章章纲            | 长期滚动规划、全书改线、受影响章节分析              |
| 质量     | 逐章事实一致性、版本化审阅修订、前五章联合复核          | 作者风格学习、长程因果与人物弧光、人机协商          |
| 发布     | 首发资料、五章 TXT/Markdown、备份，手工上传             | 多平台排期、存稿运营、数据反馈；自动发布另行授权    |
| 环境     | 首先验收服务端存储与桌面浏览器，1440/1024 主流程        | local/server 深度等价、全视口和复杂离线恢复         |
| 迁移     | V1 主流程所有页面与回链在新平台内完成                   | 其余高级功能迁移与兼容旧界面彻底退出                |

V1 不删除现有高级能力、不破坏旧数据。旧包名、存储键、数据库兼容字段不为品牌统一而强行重命名。V1 不以封面生成、关系图编辑、CSV 指标、复杂导入、全部旧平台功能验收作为阻塞。

## 4. V1 作者实际流程

1. **配置 AI**：填入服务端安全保存的 API Key，选择 DeepSeek V4 Flash，连接检查通过。首页指出未配置项。
2. **描述想写的书**：一句话构思、题材、受众、核心爽点/阅读承诺、主角目标、风格、禁区、预计规模、每章字数。提供可编辑默认值，不让作者填工程参数。
3. **确认开书方案**：沿用已有候选机制；作者选定一个方案后形成版本化基线，显示采用了哪些定位和设定。
4. **生成全书规划**：书名/简介/卖点；全书起承转合、主线冲突、高潮与结局方向；各卷目标、转折、人物成长、关键伏笔；首卷展开和前 10 章可执行章纲。大纲覆盖全书方向，不要求开写前写完数百章细纲。
5. **准备首发五章**：每章章纲包括目的、视角、时间地点、登场人物、冲突、关键事件、信息揭示、情绪/爽点、章尾牵引、禁改事实和字数目标。界面显示准备完成与缺失项。
6. **启动连续创作**：限定第 1—5 章、目标字数、重试上限和用量预算。支持逐章确认；如果作者明确选择批次自动采纳，只授权这五章，锁定设定冲突仍停下来处理。
7. **逐章形成正式稿**：生成→检查→必要修订→复检→确认正式正文→同步摘要/事实/时间线→下一章。可暂停、返回、重启后继续；失败保留成果并说明下一步。
8. **首发检查与导出**：前五章联合报告、书名/简介/标签/章节目录、最终正文；生成 TXT、Markdown 和备份。作者审读后手工上传目标平台。实际发布日期/平台/链接由作者填写。
9. **继续连载**：重新进入作品，能够基于前五章正式状态启动第六章，不重新开书、不丢失前文。

建议首页采用一个“开书进度”区块，依次显示方案、规划、设定、首发五章、发布准备；每步有唯一主要动作与可回到已有成果的入口。优先串联现有页面，避免再造一套脱离现有数据库的演示向导。

## 5. DeepSeek 接入要求

2026-09-09 查阅官方资料：OpenAI 兼容 base URL 为 `https://api.deepseek.com`，模型 ID 为 `deepseek-v4-flash`；官方列出 JSON Output、Tool Calls 和思考/非思考模式。来源：[首次调用](https://api-docs.deepseek.com/)、[模型能力](https://api-docs.deepseek.com/quick_start/pricing/)。

- V1 优先复用已有 openai-chat 通路。若实测证明现有通路不满足需要，再按证据做最小适配；不要同时新增多个协议工程。
- 开书、规划、正文、审稿、修订、结算各岗位均需解析到指定模型，不能仅更改设置页显示名称。每次调用记录脱敏后的供应商、模型、任务、用量、耗时、结束原因。
- 逐项验证结构化对象、长正文流、工具回合（仅实际流程使用时）、推理输出与正文隔离。不能把 JSON Output 自动等同于任意 strict JSON Schema 兼容。Schema 本地校验必须保留，能力降级需可追踪。
- 401/余额不足停止并解释；429/临时网络错误指数退避；截断继续或重生成对应候选；不能把半章当成完成。建议瞬态重试最多 2 次，单章质量修订最多 2 轮，达到上限转作者处理。
- 设置批次调用数、token、时间预算和可配置费用预算；估价必须注明费率来源/日期，无法准确估价就显示真实 token，不伪造费用。质量不达标不无限循环烧费用。
- API Key 使用现有服务端凭据机制或被 Git 忽略的环境配置；不放浏览器 localStorage、源码、报告、截图和日志。不要让用户在公开文本里提交密钥。
- Key 尚未提供时先完成可独立的实现、模拟异常测试和操作说明；真实模型验收标记“待凭据”，不能称 V1 已完成，也不能反复空转调用。

## 6. 质量与一致性：可检查的门槛

每章上下文至少包含：已确认创作基线版本、当前章纲/简报、相关人物身份动机与状态、世界硬规则、时间顺序、未回收伏笔、前文正式摘要和最近章节必要正文。优先保留硬约束，截断或检索失败必须记录缺失，不能默默丢失。

检查分三层：

| 层级       | 要查什么                                                                                   | 处理                                                 |
| ---------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 确定性     | 字数、空正文、截断结束原因、占位符、明显重复段落、章节序号与版本                           | 失败禁止进入首发包；不靠灌水凑字数                   |
| 语义一致性 | 人名身份、知情范围、能力代价、物品伤势位置、时间先后、因果、既有事实与伏笔                 | 输出章节/版本/引用片段/依据/严重度；阻断问题修订复检 |
| 阅读质量   | 首章有效进入事件、主角目标、冲突升级、叙事清楚、人物行动动机、对话区分、信息密度、章尾牵引 | 分项说明与建议；逐章审读，并做前五章联合检查         |

单独审稿请求应以文本和权威设定为依据，不以写作模型自己的“我已满足”作为证据。同一模型自审仍有盲点；作者最终审读保留。质量目标是降低可识别的矛盾与低质风险，不能承诺市场成绩、平台审核通过或绝对不存在矛盾。

建议默认每章目标 2500 字、验收区间 2000—3500 字，五章有效正文不少于 10000 字；标题、空白、Markdown 标记、思考过程不计入，统一界面与后端的计数口径。偏好可以调整，但验收样本不能降到数百字规避长文难点。所有阻断问题必须解决；剩余警告逐项列出。修改正文后旧报告标为过期，对应正式版本重新检查。

正文、摘要和事实更新须通过既有事务或可恢复的幂等状态机保持一致。第 N+1 章开始前验证第 N 章已正式保存且结算完成。不要在审稿过程中静默修改锁定设定来“消除”矛盾。

## 8. V1 最终验收材料

在 `docs/releases/v1/` 保存不含凭据的报告和作者使用说明；正文与数据库放本地受控产物目录，是否提交文学正文单独说明，避免意外把私人素材进 Git。

- 工作树/提交基线、运行环境、模型 ID、脱敏配置、时间、用量、总耗时和失败恢复记录。
- 一个全新作品的 project/session/run/document/version ID 对照；全过程由新平台正常入口触发，不能直接插入数据库或靠 `/advance` 接口冒充后台能力。
- 创作基线、全书/分卷大纲、前 10 章章纲、故事设定的可读取成果。
- 五章最终正文，各章有效字数、最终版本、摘要/结算状态、审稿问题与复检结果。
- 前五章联合质量报告；阻断问题为 0；明确待作者判断的警告。
- 暂停/恢复、刷新、服务重启后回到作品和任务的证据。测试失败恢复不重复消耗已完成章节。
- 首发 TXT/Markdown、备份文件及 hash；导出章节顺序/正文对应版本校验；备份恢复后的正文与设定可读。
- 第六章基于前五章状态继续生成的候选与来源回执，证明没有把第五章硬编码为故事终点。
- 主流程浏览器证据和最终检查结果。模拟模型可用于回归，但不能替代上述真实模型结果；skip 不算通过。
- “可以发布”的含义为已形成可审读、可手工上传的稿件及材料；未操作第三方平台时，不标记为“已刊登”。

## 9. V2 迭代内容与接续条件

仅在 V1 有真实五章交付证据后启动 V2。优先围绕作者实际改稿痛点排序：

1. **共创工作台**：选区对话、指令可撤销、多个候选比较、细粒度采纳、三方差异合并和自动保存冲突恢复。
2. **改线与影响分析**：修改人物/世界/结局前展示影响哪些大纲、正文、摘要和伏笔；选择保留旧版本或生成修订，不静默批量覆盖。
3. **长篇记忆**：关系/人物状态/时间线可视化编辑、伏笔计划与回收、跨卷因果追踪、作者风格约束和中长期质量评估。
4. **连续创作控制**：批次中插入作者指令、重规划安全边界、分支试写、可比较方案和预算策略。
5. **运营与平台能力**：存稿、排期、发布记录、指标导入与反馈；封面/简介辅助根据实际需求补齐。
6. **全平台完善**：复杂导入、全部旧能力原生覆盖、移动端体验、双存储模式完整验收、高级资产和模板管理。

长期缺口仍参考 06/08/09/10 与迁移矩阵。V1 收敛的是交付顺序，不是取消彻底改造。
