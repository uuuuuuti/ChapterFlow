# ChapterFlow V1 作者使用说明

这份说明对应 ChapterFlow 新平台的 V1 主链：构思、AI 开书、确认方案、生成大纲与章纲、逐章写作、审阅修订、导出、备份恢复和继续连载。

## 1. 启动与安全配置

在仓库 `/Users/armray/Documents/ChapterFlow`：

```bash
npm install
npm run dev
```

打开 Web：`http://127.0.0.1:4318`。服务端 API 为 `http://127.0.0.1:4317`；启动后访问 `/api/health` 检查数据库和迁移状态。

在服务端受控、已忽略的环境文件中配置：

```dotenv
NARRATIVE_LLM_API_KEY=<你的 DeepSeek API Key>
NARRATIVE_LLM_BASE_URL=https://api.deepseek.com
NARRATIVE_LLM_MODEL=deepseek-v4-flash
NARRATIVE_LLM_CONTEXT_WINDOW=128000
NARRATIVE_LLM_MAX_OUTPUT_TOKENS=32000
NARRATIVE_DATA_DIR=./data-v1
NARRATIVE_BACKUP_DIR=./data-v1/backups
```

不要把 key 放进浏览器 localStorage、代码、提交记录、截图、导出稿或日志。进入“设置”确认模型显示为 `deepseek-v4-flash`，执行文本、SSE、工具、structured JSON 连接测试；四个阶段都通过后再开始消耗真实额度。假模型只能用于回归，不能替代真实模型验收。

## 2. 新建作品与 AI 开书

1. 从“我的作品”点击“新建作品”，或打开 `/books/new?mode=ai`。
2. 输入题材、读者、核心设想、主角目标、风格、禁区和希望兑现的阅读体验。
3. 等待 foundation 候选，比较定位、主线、高潮、终局、人物、世界、事实和伏笔。
4. 只对满意的方案点击“采用/确认”；确认后刷新页面，检查故事设定、大纲和任务中心都能读到正式数据。

确认后平台会把方案保存为可追踪的作品资料，不只留在一次对话里。修改锁定事实前先确认不会掩盖已经写出的正文矛盾。

## 3. 大纲、设定和前 10 章章纲

在“作品设定”检查人物、世界、事实、时间线、伏笔；在“大纲”检查书、卷、篇和章节顺序。前 10 章章纲应逐章具备：

- 本章目标与冲突
- 事件、时间、地点和出场人物
- 信息揭示
- 章尾牵引
- 禁改事实
- 目标字数

大纲页会区分“卷 ·”“篇 ·”和“章节”，编辑下拉使用“第 N 章 · 标题”。重新规划留下的 abandoned 节点只作为历史证据；没有绑定正文的历史章节不会再出现在当前写作树中。已有作者正文的历史节点仍保留，避免隐藏稿件。

章纲保存后可以刷新验证。后续生成会消费权威设定、人物当前状态、时间线、未回收伏笔、已确认章纲、前文摘要和必要正文；没有 embedding 时仍使用必要文本上下文。

## 4. 逐章或批次写作

从“连续创作”进入正常服务端 worker。V1 建议默认一章一确认：

- 目标字数：2500
- 验收范围：2000—3500 有效字符
- 最大瞬态重试：2
- 最大质量修订轮数：2
- 先做一章纵向流程，再明确授权五章批次

五章批次前先确认预算、余额和授权范围。只有明确限定的批次授权可以自动采纳；硬约束冲突、作者新稿或版本冲突必须停下来。每章依次执行章纲→上下文→草稿→确定性检查→语义审阅→必要修订→复检→正式版本→摘要/事实结算→下一章准备。模型截断、占位文本、明显重复或低于 2000 字都不算完成。

任务中心可以查看 run、步骤、错误和产物。暂停后可刷新页面再恢复；服务重启后重新打开任务中心，先确认 run 状态，再从未完成步骤继续。失败会保留已有候选。不要连续点击生成，已完成章节不会因刷新重新生成。

## 5. 审阅、修改与版本

审阅报告必须绑定章节和正文版本，并给出具体引用、依据、严重度和建议。重点检查人物知情范围、因果、能力代价、地点/物品/伤势状态、时间线和伏笔回收。

1. 先看确定性检查的有效字符数、重复和硬约束结果。
2. 再看语义审阅的证据段落。
3. 采用修订会创建新版本；修订后重新检查最终版本。
4. 不要用修改锁定设定的方式掩盖正文矛盾。
5. 对 minor/info 逐项决定修改、保留或记入后续章纲。

作者自己编辑后的正文应先保存，再请求检查；平台不会覆盖作者的新稿。历史审阅报告不会冒充当前版本待办。

## 6. 导出首发材料

进入“发布”，文件格式选择 Markdown 或纯文本（TXT），起始章节和结束章节选择首发五章，版本上下文选择“当前正文版本”。先预览，核对标题顺序和章节数，再下载。下载后可用：

```bash
shasum -a 256 data-v1/exports/v1-acceptance/潮痕档案：第七码头.md
shasum -a 256 data-v1/exports/v1-acceptance/潮痕档案：第七码头.txt
```

平台只记录导出批次，不自动登录或上传第三方站点。作者完成实际上传后，再自行记录平台、范围、日期和链接；未上传时不要创建“已发布”记录。

## 7. 备份与恢复

在发布页填写备份说明，点击“创建备份”。恢复时点击对应快照的“恢复为新作品”，确认后系统创建新作品，不覆盖原作。相同 backup ID 恢复成功后再次操作会返回原来的恢复作品，不会生成第二个副本；刷新发布页也不会重复创建。

打开恢复作品的 dashboard、设定、写作和审阅页，确认章节、版本和报告可读，再把恢复作品作为继续创作的副本。作品备份 bundle 保存在服务端数据库 `data-v1/narralume.sqlite` 的 `project_backups` 表；服务端数据库级安全快照保存在 `data-v1/backups/`。这些私人数据都不要提交仓库。

旧数据库中此前已经创建的同名作品或恢复副本不会被平台静默删除。作品库会标出“恢复副本”和“同名副本 n/m”；确认不需要的旧副本后，再通过作品库的回收站处理。

## 8. 继续第六章

回到作品 dashboard 的“继续写作”，或从“连续创作”选择下一份已保存章纲。保持目标 2500、范围 2000—3500，并选择逐章确认。生成后先看章纲、正文长度和证据型审阅，再点击“接受正文”；需要修改时使用“请求重新修改”。只有作者确认后第六章才成为正式版本，五章首发导出不会被它悄悄改变。

## 9. 真实模型与故障边界

真实模型门必须始终显示官方 base URL 和精确 model ID。401、余额不足会停止并提示；429 或瞬态网络错误只在预算内重试；截断会保留候选并要求继续或重生成。达到重试/修订上限后转作者处理，不无限烧额度。

若 API key 缺失或额度不足，先保存本地工作和任务上下文，把真实模型门记录为 `blocked`，补充安全配置后再继续；不要降级到 mock 后宣布完成。用量、失败、重试和恢复记录以任务中心与验收报告为准。
