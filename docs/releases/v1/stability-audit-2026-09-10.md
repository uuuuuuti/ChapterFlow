# ChapterFlow V1 稳定性复核

审计日期：2026-09-10。性质：只读诊断与下一轮实施建议；不是新的验收通过报告。

## 结论

当前是“有真实模型与正文产物、主链部分跑通，但验收范围和版本闭环不可靠”的 V1 候选版本，不能继续沿用 G0—G6 全部 passed 的结论。优先修业务不变量和用户闭环，不重建平台、不扩到 V2。

依据为 `docs/refactor/11-two-release-plan.md`、现有验收文档、服务与前端源码、运行中 API、只读 SQLite 查询和真实浏览器。原作品 ID：`a42fb546-6eb4-49fe-b97b-fb23482ce2c7`。本轮未修改产品代码或业务数据，未消费真实模型额度，未重跑完整测试。此前完整检查通过属于历史记录，不是本轮验证结果。

本文区分“已确认”“代码风险”“待验证”：没有重现的故障不写成已经发生；没有证据的门不标 passed。历史报告保留以便追溯，其通过结论应由后续重新验收取代。

## 2. 当前正文、审阅、结算未形成同版本闭环（P0，已确认）

只读查询以 `documents.current_version_id` 关联 `document_versions`，审阅匹配版本 ID 或正文 hash，结算摘要匹配 `narrative_summaries.source_hash`：

| 当前正文             | 匹配当前版本/hash 的审阅条数 | 匹配当前正文 hash 的结算摘要条数 |
| -------------------- | ---------------------------: | -------------------------------: |
| 反刮的页码           |                            0 |                                0 |
| 执行名单上的我的名字 |                            0 |                                0 |
| 机房里的审计员       |                            3 |                                0 |
| 陈字班次             |                            3 |                                0 |
| 低潮时启门           |                            3 |                                1 |
| 雾转瞬间             |                            3 |                                0 |
| 三名未入册者         |                            3 |                                0 |

“3 条”不表示三项检查全部通过，只表示存在匹配记录。七章已有七份 chapter summary，但其中六章没有当前正文 hash 对应摘要，因此不能说最终版本均已结算。前两章有开篇检查不能替代最终语义审阅。

六章当前版本 source 为 `manual:...`；`packages/services/src/story-routes.ts:1683` 仅在 source 严格等于 `manual` 时触发该保存路径的结算。`packages/narrative/src/workers.ts:406` 与 `:446` 取 latestSummary 时未在这里校验对应正文 hash，存在“新正文配旧摘要”风险。正常 worker 在 `:1564`、`:1574` 保存 sourceHash/sourceDocumentVersionId，说明可复用既有版本绑定，不需要另造系统。

修复验收：所有作者保存/采纳入口统一版本变更事件；审阅、摘要、事实与人物状态都可判断 current/stale/pending/failed。前章最终版本未完成有效结算，不得把批次算完成或向下一章消费过期结算；修订产生新版本须重新审阅和幂等结算。历史事实撤回/替代必须可追踪，不能简单叠加矛盾事实。

## 3. 上下文顺序与目录顺序不一致（P0，已确认实现问题）

`packages/narrative/src/outline-context.ts:18` 使用 `path.localeCompare` 排序。当前 path 含 run UUID，实际字典序将 `ea7...` 篇章中的全书第 6、7 章排在 `f5...` 篇章中的第 1—5 章前面。由此计算 nearBefore/nearAfter 和结构摘要，前后关系会错位。不能据此断言每次模型都写错，但上下文构造已不满足正确章序。

修复验收：显示、写作、审阅、上下文、批次范围、导出共用按祖先 ordinal 的树顺序；覆盖随机 ID、跨篇移动、同篇超过 10 章、重排。未来章纲可作为规划输入，但不能被当作已发生事实或角色已知信息。

## 4. 质量闸门允许不合格稿继续（P0，已确认代码分支；需回归重现组合）

- `packages/harness/src/router.ts:198`：在 autopilot/chapter-gate 下，`revise` 且没有 critical 时允许进入 chapter.settle。没有在这一分支阻止 unresolved major。
- `:340` 只取最后一个成功 deterministic/semantic gate，不是同一最终内容上两类结果的合取。最后一个 semantic pass 存在掩盖确定性失败的风险。
- `packages/narrative/src/workers.ts` 的确定性检查对有 issues 输出 revise，包括 critical；具体组合必须用真实 recipe 测试，而不是仅测 helper。
- `packages/services/src/run-policy.ts` 的 manuscript acceptance safe 主要保护版本并发和作者草稿，不等价于质量合格。

保留不合格候选给作者是合理的；把它自动结算、定稿、计数或续章则不符合 V1。需要区分保存、作者采纳、质量合格、发布范围验收，而不是一个 completed 包打天下。

修复验收：同一最终内容 hash 上，字数/截断/占位/重复/硬约束和最终语义检查同时满足；critical 与 V1 阻断类 major 为 0，修订上限耗尽必须等待作者处理，不靠自动提交跨过质量门。

## 5. 联合审阅与全书规划证据不足（P0/P1，待验证）

当前原作品 runs 中有 document-review、chapter-production、rolling-outline 等，但未发现独立的前五章联合审阅 recipe；旧报告也未给出覆盖准确五个最终版本的联合审阅证据。`autopilot-coordinator.ts:146` 在完成章数达标时直接完成 session，不能假设有 closing-review 类型就必然执行过联合审阅。

`workers.ts:995` 语义审阅提示词最多报告三个问题。这是控制输出长度的措施，不是充分检查全部阻断问题的证据；需要覆盖维度、分段/分项检查或其他有界机制，不宜仅把上限无限调大。

旧报告用三轮 rolling-outline 和十份高级工具章纲说明完整规划。当前只有一个 volume；一个 volume 本身不是错误，但“全书主线/高潮/终局与分卷规划的正式版本、确认关系，以及写作实际消费这些内容”需要逐项证明，不能用当前窗口滚动计划替代全书规划。十份章纲存在也不证明普通作者入口能自动形成并确认它们。

修复验收：新建作品的普通流程可保存完整规划与十份结构化章纲；context receipt 证明消费确认版本。前五章联合报告绑定准确五个最终 hash，覆盖时间线、知情边界、因果、能力代价、物品/地点/伤势、伏笔；版本变化使联合结论失效。

## 6. 用户看到的“重复”有四种来源（P1，已确认）

1. **作品副本**：原作品外有两个恢复作品，ID 分别为 `84040e82-b6e3-4e6f-bf34-7528d1944dd1`、`d6987f4a-3dae-450c-b109-9f1d1ccb3365`，同名“雾港第七码头 · 备份恢复”，被当作普通创作中作品。恢复验证污染作品库和统计。
2. **页面复现同卡片**：`library-page.tsx:93` 的最近创作与全部作品都展示相同作品；这是展示策略而非新增 DB 行，但放大了重复感。
3. **同名篇章**：`封存早于行程` 有两个不同 arc，分别来自 ea7 与 fd 两轮滚动规划；章节点目前十个不同标题，不能笼统说章节都重复。`automation-workers.ts` 优先填空骨架，否则新建 run-id arc，缺少明确续接篇章语义。两个 arc 的内容不同，不可仅按标题合并。
4. **导出记录**：`publish-page.tsx:306` 明确每次预览或下载都留下批次。预览加下载出现同名同内容记录是当前设计，不一定是网络重复提交。

另有两个作品备份，标签、时间、hash 不同，是两次快照，不能武断删除为重复备份。恢复按钮每次调用生成新 request ID（`publish-page.tsx:132`），同一次未知结果的重试可能产生额外副本；这是需断网/重试测试的幂等风险。

修复验收：恢复副本标来源、时间、用途，可查上次恢复并选择打开/另建；同一恢复意图复用幂等键；测试副本可明确归档且不污染活跃统计。普通作品允许同名，身份由稳定 ID 判定。预览与正式下载记录可区分或合理合并。已有数据处理先列确切目标及版本变化，保护作者后续编辑，默认不删除、不自动合并。

## 7. 发布质量状态与作者操作不一致（P1，已确认显示问题）

当前全书有七章正文、三章尚无正式版本；接口已有空文档记录。此前质量分从 96 变 75，当前问题包含空正文等全书统计；不能把计划中的第 8—10 章直接当成首发第 1—5 章范围的阻断。`publish-page.tsx:192` 展示 score/gates，没有逐项展示 quality.issues，因此用户不易解释扣分或跳转修复。

旧报告的全书 readiness blocked 与“五章可交付”之间缺少可见的范围级结论。全书提醒应保留，但应与选定首发范围分开；总分不是正文最终审阅。

修复验收：页面列出选定范围、最终版本状态、阻断/警告、原因与直达解决入口；计划章节不因创建空编辑文档而突然变成新增质量缺陷；历史审阅与当前待办分离。导出草稿可以保留，但不得把草稿导出写成 V1 通过。

## 8. 可携备份和首发材料交付不完整（P1，部分已确认）

`data-v1/exports/` 目前找到 TXT、Markdown 两份正文；未在该交付目录找到独立首发书名/简介/标签/目录材料及可携作品备份包。不能由此证明平台没有相关能力，但现有交付证据不足。

作品备份存在 SQLite 的 `project_backups.bundle_json`；`data-v1/backups/` 是系统 SQLite 快照目录。旧报告把二者混写。恢复后 reports/issues 数量可读，仅证明反序列化部分成功，不能证明当前版本、引用重映射、设定状态和可续写等价。

另外 `delivery-service.ts:1144` 用 `bundleJson.length` 填 sizeBytes。两个备份实际 UTF-8 大小分别为 977028 / 1144318 bytes，记录却为 482211 / 576884；中文长度不是字节长度。

修复验收：交付可下载的作品包及 manifest，明确区别系统备份；在隔离恢复环境核对章节顺序、正文 hash、版本关系、审阅引用、章纲和设定/结算，再通过正常入口继续写。包内排除凭据；恢复的历史 run 不应伪装成当前真实执行或重复计费用。

## 9. 预算、恢复与启动可重复性（P0/P1，代码风险及验证缺口）

- 历史报告记录 232 calls、input 4081358、output 887218，说明“跑通”成本不可忽略；这不是本轮新增费用。未配置费率的 0 应显示“金额未知”，累计调用耗时也不应冒充墙钟耗时。
- coordinator 本层未见整个 session 跨子任务统一 calls/token/time 硬预算。已有 run budget 不能直接证明五章总预算。需沿服务层预算路径验证，缺失则补齐；失败后新建 run 不能刷新额度。
- 创建 chapter run、attachRun、更新 outline，以及 markRunProcessed 与累计 completed 的调用分散。不能仅凭没有看到外层 transaction 就断言必丢数据；应对这些边界做中断恢复测试，证明没有孤儿 run、漏计、重复写作和漏结算。
- nextChapter 对不存在的范围端点回退到开头/结尾，存在扩展授权范围风险；无可写章节时进入 rolling plan，也需验证限定五章授权不会越界。
- monorepo 部分依赖从 dist 导出，Vitest 仅 narrative 映射源码；历史修复中曾需 force build 才消除旧行为。需要证明作者说明中的启动步骤在干净构建产物下可复现，不能依赖代理事先手动编译。
- 根 `npm run verify` 不包含 browser E2E；`verify:release` 的旧真实 smoke 矩阵也不天然等于 V1 用户流程。已有 808 tests 通过不能证明以上业务不变量。

## 10. 页面与交互范围

本轮 Playwright 在 `/books`、1024×768 复核了同名恢复副本和重复卡片；documentWidth 1013、viewport 1024，该页没有发现根级横向溢出，不泛称“所有布局坏了”。

`outline-page.tsx:510` 折叠控件为外层按钮里的 span role=button，仅有 click，无独立键盘焦点与键盘处理；不是两个原生 button 嵌套，但存在可访问性与操作语义问题。

仍需在 1440/1024 桌面实际走开书确认、章纲编辑、正文保存/离开、审阅定位、暂停/恢复、错误重试、发布范围和备份恢复。重点是主要操作可找到、状态可解释、不丢编辑、错误有回链，而不是全面视觉重做。

## G0—G6 重新评估与实施顺序

以下状态属于复核，不覆盖历史记录。pending 表示需要重新验收，不表示能力完全不存在。

| 门  | 复核状态 | 主要缺口                                                 |
| --- | -------- | -------------------------------------------------------- |
| G0  | doing    | 启动运行已观察；可靠复现、隔离验收数据和范围证据待补     |
| G1  | pending  | 有历史真实模型证据；最终构建下六岗位精确解析与总预算待验 |
| G2  | pending  | 全书规划、十章普通入口确认与上下文消费待验               |
| G3  | pending  | 真正第一章当前版本审阅/结算不完整                        |
| G4  | pending  | 首五章范围错配、版本闭环和联合审阅不足                   |
| G5  | pending  | 导出范围错配、第八章冒充第六章、可携包和恢复等价待验     |
| G6  | pending  | UX、幂等/中断恢复、当前构建完整检查与浏览器回归待验      |

推荐四阶段：①顺序、版本闭环、质量与预算不变量；②完整规划与第一章普通入口；③重复/恢复/发布交互与有界五章生产；④隔离恢复、第六章及真实交付。每阶段先针对性回归，最后一次完整检查和真实浏览器链路，避免反复全套测试消耗时间。

对应可直接执行的 Goal 提示词见 [luna-max-stabilization-goal.md](luna-max-stabilization-goal.md)。
